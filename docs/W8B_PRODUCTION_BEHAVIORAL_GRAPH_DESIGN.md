# W8B — Production Behavioral Graph: Migration Design (Review Only)

**Status:** Design review only. No implementation, no production code, no serving change,
no schema change. No existing file is modified by this document.

**Premise (from the completed W8A audit):** MIND item IDs do not overlap production article
IDs; a MIND `FeedbackGraph` cannot be transferred into production; W8 validates the behavioral
*method*, not transferable weights; **production must build its own behavioral graph from its
own reads.** This document audits how production would evolve from today's synthetic base graph
to a real behavioral one.

---

## Part 1 — Current production architecture

Everything is built by `Backend.__init__` (`examples/api_server.py:519-599`), **once at
startup**, then reused as immutable state under the threadpool.

### Click matrix
- **Base corpus (today, live):** generated by the repo's own agent simulator —
  `import simulate_users as su; … su.run(cfg, qbias=profile.qbias_csv)`
  (`api_server.py:540-542`). Items are the **real** Qbias catalog; **users and clicks are
  synthetic** (`simulate_users.py:6-7`). The result is a `MINDData` whose `dataset.matrix` is
  the click matrix (`api_server.py:543`).
- **npz profile:** `MINDData.load(profile.npz)` (`api_server.py:534`) — a pre-ingested corpus.
- **Per-user augmentation (real reads today):** `personalize._build_model`
  (`personalize.py:197-236`) calls `augmented_corpus.augment(base, reads)`
  (`augmented_corpus.py:134`) to append **one real reader row + novel columns** onto the base
  matrix, then rebuilds the recommenders over the augmented corpus.

### Item positions
- `mind.item_positions` — Qbias **gold AllSides lean** (synthetic path) or outlet-registry lean
  in the real ingest path (`examples/ingest.py` via `outlet_registry`). Novel columns carry the
  read's scored `lean` (`augmented_corpus.py:181-182`). `recommender_inputs` **drops NaN-position
  items** (`rwe/mind.py:366-384`).

### User positions
- `mind.user_positions` — the **true synthetic viewpoints** for simulated agents
  (`simulate_users.py:21-22`); for an appended real reader, the **click-mean of their reads'
  registry leans** (`augmented_corpus.py:187-193`), else the click-mean proxy
  `user_positions_from_clicks` inside `recommender_inputs` (`rwe/mind.py:371-372`).

### FeedbackGraph
- `Backend._build_recommenders(self.mind)` → `FeedbackGraph(rec_dataset.matrix)`
  (`api_server.py:592`; `rwe/graph.py:34`). Built from the **click matrix only** — bipartite
  adjacency `A^G` (`graph.py:57-62`) and transition `P = D⁻¹A^G` (`graph.py:64-71`). No outlets,
  no positions enter the graph.

### Random walks
- `FeedbackGraph.item_distribution(user_ids, k=3)` (`graph.py:118`) — the k-step walk mass over
  item nodes, consumed by every RWE recommender's `_score_batch` (`rwe/random_walk.py`), which
  re-ranks that walk output using `item_positions` (RWE-B bridging) / degree (RWE-D).

### Where simulated users are used
- **The entire base corpus** for the synthetic/Qbias profile (`api_server.py:540-550`). Also the
  `simulate_users.py` CLI, `demo_synthetic.py`, eval harnesses, and tests. This is **Stage 0**.

**Key architectural fact:** production is *already a hybrid* — a **synthetic base graph** plus
**per-user real-read augmentation** for any reader at/above the read threshold. The migration
below replaces only the **base**, reusing the augmentation seam unchanged.

```
                       Backend.__init__ (startup, once)
  profile ──► simulate_users.run() ─► MINDData(base)  ─► _build_recommenders ─► FeedbackGraph(base)
                                          │  item_pos = gold/registry lean          │
                                          │  user_pos = synthetic viewpoints        │ item_distribution(k=3)
                                          ▼                                          ▼
  real reads ─► augmented_corpus.augment(base, reads) ─► FeedbackGraph(base ⊕ reader) ─► RWE feed
   (≥5 reads, per user, cached)              (1 row + novel cols)
```

## Part 2 — Can existing code build a production behavioral graph from reads?

**Can we build `Dataset.from_interactions` from production reads? Yes — the primitive exists.**
`from_interactions(users, items)` (`rwe/data.py:39`) builds a sparse matrix from any parallel
`(user, item)` arrays. Production reads are already persisted in the `Read` table
(`store.py:249`).

**Which modules already support this:**
- `rwe/data.py:39` `from_interactions` — matrix builder.
- `rwe/graph.py:34` `FeedbackGraph` — graph from the matrix.
- `examples/ingest.py` `Scorer` — scores each read → lean / outlet / topic (→ `ScoredRead`).
- `examples/augmented_corpus.py` — `ScoredRead` + `augment` (the per-user precedent; the exact
  join logic a multi-user builder would generalize).
- `rwe/mind.py:366` `recommender_inputs`, `rwe/mind.py:322` `fit_ideology` (optional co-click
  positions), `rwe/mind.py:405` `save` (serialize the corpus/graph as an `.npz`).
- `examples/export_reading_history.py` `--all-users` — the precedent for **enumerating every
  user's reads** (it iterates users via local read-only SELECTs; "no Store method exposes those",
  `export_reading_history.py:5-6`).

**Which modules would need to change / be added (offline only):**
- **One new offline builder** — the only genuinely missing piece: enumerate *all* users' reads
  (there is no bulk accessor; only per-user `get_reads`/`list_reads`/`count_reads`,
  `store.py:1016-1041`), score them, `from_interactions` → matrix, attach registry-lean
  `item_positions`, wrap as `MINDData`, `save()` an `.npz`. It is a **generalization of
  `augment()` from 1 user to N users** and reuses every primitive above. It lives entirely
  offline (a script/notebook), touches no serving path.
- Optionally a small **bulk-reads read-only query** on the store (a convenience over the
  `export_reading_history` iteration). Read-only; not a schema change.

**Is the graph incremental or rebuilt offline?** **Rebuilt offline (batch).** `FeedbackGraph`
is **immutable** — `A^G`, `D`, and `P` are all computed in `__init__` (`graph.py:47-71`); there
is no edge-insert / renormalize API. Today the base graph is built once and replaced wholesale;
per-user augmentation rebuilds a *small* augmented graph per reader and caches it
(`personalize._build_model`, keyed on `reading_version`). A behavioral **base** would follow the
same batch-rebuild-then-swap model, not in-place mutation.

**Would this require downtime? No.** `corpus_refresh.RefreshController` already performs
**atomic, off-request-path hot swaps**: build a new `Active` bundle (backend + personalizer,
same generation), run sanity checks, then `app.active = new` — a single pointer assignment
(`corpus_refresh.py:4,12-18,50`). Failure never swaps (rollback by construction); an unchanged
signature rebuilds nothing (idempotent). A behavioral-graph rollout reuses this exact mechanism.

**Would this require schema changes? No.** Reads are already stored (`Read`, `store.py:249`);
item positions come from the existing outlet registry; the behavioral graph is a *read* of
existing data plus an on-disk `.npz` artifact (a file, not a DB migration).

## Part 3 — Migration strategy (safest path)

The invariant across all stages: **a reader's identity and the augmentation seam never change —
only the `base.mind` they are grafted onto changes.**

| Stage | What runs | Reader experience | Serving change? |
|---|---|---|---|
| **0. Synthetic (today)** | Synthetic base graph + per-user real-read augmentation | Cold → demo/Initial Estimate; ≥5 reads → augmented onto synthetic base | — |
| **1. Collect reads only** | Reads accumulate in `Read`; graph unchanged | Identical to Stage 0 | None |
| **2. Offline behavioral graph** | New offline builder: store → `from_interactions` → `FeedbackGraph` → `.npz` | Identical (artifact not served) | None |
| **3. Compare synthetic vs behavioral** | W8A metric battery on the production behavioral graph vs the synthetic one (offline) | Identical | None |
| **4. Shadow evaluation** | Compute recs from **both** graphs; log divergence + metrics; serve only synthetic | Identical (shadow is silent) | None (shadow only) |
| **5. Optional rollout** | Swap base profile synthetic → behavioral-`.npz` via `corpus_refresh` hot-swap, flag-gated, canary → all | ≥5-read readers now augmented onto the **behavioral** base; cold readers unchanged | Base-corpus swap only |

**How readers transition between stages:**
- **Cold readers (`count_reads < 5`, `ESTIMATE_MIN_READS`, `api_server.py:478`)** are served the
  base/demo path in *every* stage — they never touch the behavioral graph until they cross the
  threshold, so Stage 5 changes nothing for them.
- **Measured readers (`has_measured`, `count_reads ≥ 5`, `personalize.py:145`)** are augmented in
  every stage; at Stage 5 the *only* difference is `base.mind` (synthetic → behavioral). The
  `augment()` call, cache keys, report contract, and explain plan are byte-identical.
- **Rollout cohorting** at Stage 5 is by base-profile selection behind a flag (canary cohort
  first), with instant rollback = swap the pointer back to the synthetic base.

```
Stage:  0 ───► 1 ───► 2 ───► 3 ───► 4 ───► 5
        synth   collect  offline  compare  shadow   swap base
        base    reads    build    A vs B   (silent) (flag/canary→all, rollback=swap back)
        └──────────────── augmentation seam identical throughout ────────────────┘
```

## Part 4 — Cold start (new users after W8)

Thresholds are all in code:

- **Augmented path activates at ≥ 5 reads** — `ESTIMATE_MIN_READS = 5` (`api_server.py:478`);
  `has_measured = count_reads ≥ 5` (`personalize.py:145`). Below 5 → Initial Estimate / demo.
- **A reader is an eligible base-corpus node at ≥ 5 clicks and ≥ 3 political**
  (`_eligible_pool(pop, 5, min_political=3)`, `api_server.py:573`).
- **Ideology fitting** (`fit_ideology`, `rwe/mind.py:322`) is a **population** fit, not per-user;
  it needs enough co-click density. k-core filtering (`_filter_min`, `rwe/mind.py:140`) is
  typically run at `min_user_clicks=5 / min_item_clicks=5` in eval. It is non-convex, so
  `restarts` + best-likelihood selection stabilise it (`rwe/ideology.py:138-154`); orientation
  needs ≥ 3 known-lean items (`fit_ideology orient_by_lean`).

Approximate reads required (engineering estimate, to be confirmed by the Stage-3 measurement,
not asserted as fact):

| Milestone | Approx. threshold | Why |
|---|---|---|
| Per-user θ meaningful | ~5 of the user's own reads with a known lean | click-mean over ≥ a few labelled reads (`augmented_corpus.py:187-193`) |
| Graph edges meaningful for a user | that user's articles each read by ≥ ~2–5 others | a novel/1-reader column carries no collaborative signal (`augment`, `augmented_corpus.py:160`) |
| Population ideology fit stabilises | thousands of reads across the cohort; k-core ≥ 5/5 | dense `O(users×items)` fit needs co-click mass (`rwe/mind.py:343`) |
| Recommendations improve over popularity | ≥ 5 reads (augmented path) **and** local co-click density | routing switch + walk needs neighbours |

**Does W2 already help during this period? Yes — and independently of graph maturity.** W2
(adaptive cross-cutting exposure) activates at `min_shown=3 / min_opened=1` of cross-cutting
reception (`personalize.py:132-133`), which a reader can reach well before the graph is dense.
It personalises the *dose* on the AdaptiveRWEB slice while the graph matures, and its ε-floor
(0.5) guarantees a resistant reader still gets cross-cutting content — so W2 cushions the
cold-start feed without depending on graph density. Complementary, not a substitute: W2 tunes
re-ranking of the walk output; it cannot manufacture collaborative edges. Cold readers below 5
reads still fall back to **RWE-D popularity**, which is robust to sparsity.

## Part 5 — Rebuild cadence

| Option | Complexity | Latency to reflect reads | Ops risk | Rec quality | Explainability |
|---|---|---|---|---|---|
| **A. Nightly rebuild** | Moderate (batch + swap) | ~1 day | Low (rollback by swap) | Fresh; catches drift fast | High — each graph is a pinned, diffable artifact |
| **B. Weekly rebuild** | Low | ~1 week | Lowest | Slightly stale; fine if co-clicks move slowly | High — same pinning |
| **C. Incremental update** | **High** — `FeedbackGraph` is immutable (`graph.py:47-71`); needs a new mutable structure + renormalisation | ~minutes | **High** — drift/feedback-loop surface, harder rollback | Potentially freshest | **Low** — `rec_explain` replays a fixed plan over a fixed graph; a moving graph breaks reproducible traces |

**Recommendation: B → A ramp (batch rebuild + hot-swap). Do not start with incremental.**

- Batch-rebuild-and-pin matches the existing `corpus_refresh` swap model (`corpus_refresh.py`),
  inherits its rollback-by-construction, and keeps every served graph a **reproducible, hashable
  `.npz` artifact** — essential for `rec_explain`'s fixed-plan replay and for A/B diffing.
- Start **weekly**: the behavioral (user co-click) graph changes more slowly than the article
  catalog (which already refreshes on its own candidate cadence), so weekly is defensible and
  cheapest. Move to **nightly** once read volume/drift justify the extra compute.
- **Avoid incremental initially:** it fights the immutable-graph design, undermines
  explainability and reproducibility, and enlarges the feedback-loop surface — the three things
  this product weights most heavily.

## Part 6 — Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Sparse graph (early)** | High | High | Keep synthetic base until a density gate is met; RWE-D popularity fallback for cold users; k-core `min_*_clicks` (`rwe/mind.py:140`) |
| **Graph fragmentation** (disconnected components) | Med | Med | LCC-share metric gate (W8A); `min_item_clicks`; serve from the largest component |
| **New-article cold start** | High | Med | Novel column has no co-clicks (`augment`, `augmented_corpus.py:160`); freshness gate (C4) + popularity + editorial seeding until edges form |
| **Graph drift** | Med | Med | Scheduled rebuild cadence (Part 5); drift metrics on each rebuild; pinned artifacts + diff |
| **Feedback loops / homogenization** | Med | High | W8A homogenization-over-cycles metric as a **decision gate**; W2 ε-floor (invariant 3); W1 bridge budget; independent RWE-B/RWE-D/adaptive slices |
| **Storage growth** (reads accumulate) | Med | Low | `Read` rows are small; periodic archival; the graph is one `.npz` artifact, not per-user state |
| **Rebuild cost** (dense ideology fit `O(users×items)`) | Med | Med | `max_cells` guard (`rwe/mind.py:343`); `political_subset` + `sample_users`; the walk itself is cheap sparse — only the optional fit is dense |
| **Convergence** (non-convex ideology fit) | Med | Med | `restarts` + best-likelihood selection (`rwe/ideology.py:138-154`); stability metric; pinned seed |
| **Arbitrary axis orientation** (W8A carryover) | Med | Med | Sign-invariant metrics only; orientation needs ≥ 3 labels; registry lean can orient the axis |
| **Rollback** | Low | High | Hot-swap rollback by construction (`corpus_refresh.py:16-18`); retain synthetic base as a fallback profile; flag-gated Stage 5 |
| **Reproducibility** | Med | Med | Pin seed + input-hash + MANIFEST (the `simulate_users` stamp precedent); each graph is an immutable artifact |

## Part 7 — Deliverable artifacts

### 7.1 Target architecture (post-Stage-5)

```
   OFFLINE (batch, scheduled)                        SERVING (unchanged seam)
 ┌────────────────────────────────┐        ┌──────────────────────────────────────┐
 │ store.Read (all users' reads)  │        │ Active bundle (corpus_refresh)         │
 │   └─ new offline builder:      │        │   backend.mind = BEHAVIORAL base       │
 │      enumerate → Scorer →      │  swap  │        │                               │
 │      from_interactions →       │ ─────► │   augmented_corpus.augment(base,reads) │
 │      MINDData → FeedbackGraph → │ (atomic│        │  (per real reader, cached)    │
 │      save behavioral.npz       │  ptr)  │   FeedbackGraph(base ⊕ reader)         │
 │   (+ optional fit_ideology)    │        │        │  item_distribution(k=3)       │
 └────────────────────────────────┘        │   RWE-B / RWE-D / AdaptiveRWEB → feed  │
        │ metrics + MANIFEST                └──────────────────────────────────────┘
        ▼
   W8A battery + shadow diff  ──► decision gates
```

### 7.2 Migration timeline

```
  Stage 0 ──► Stage 1 ──► Stage 2 ──► Stage 3 ──► Stage 4 ──► Stage 5
  synth base  collect    offline     compare     shadow      swap base
  (now)       reads      build .npz  A vs B      (silent)    (canary→all)
              │ no code   │ 1 new     │ reuse     │ shadow    │ reuse hot-swap
              │ change    │ offline   │ W8A       │ compute   │ + flag + rollback
              │           │ builder   │ metrics   │ path      │
   Gate:      G1 volume   G2 builds   G3 A/B win  G4 shadow   G5 rollout OK
```

### 7.3 Dependency graph (build order)

```
  rwe/data.from_interactions ─┐
  store.Read (+ bulk read)   ─┼─► [NEW offline builder] ─► MINDData ─► rwe/graph.FeedbackGraph
  ingest.Scorer / outlet_registry (item_pos) ─┘                 │
  rwe/mind.fit_ideology (optional positions) ──────────────────┘
        │
        ├─► W8A metric battery (connectivity/diversity/stability/homogenization) ─► Stage 3/4 gates
        └─► corpus_refresh.RefreshController (hot-swap) ─► Stage 5 rollout
  personalize.augment + _build_model (UNCHANGED) ── consumes whichever base is active
```

### 7.4 Production rollout plan (Stage 5)

1. Ship the behavioral `.npz` as a **selectable profile** (like `mind`/`qbias` in
   `BUILTIN_PROFILES`, `api_server.py`), behind a flag — no default change.
2. **Canary cohort** first (a small measured-reader segment), served from the behavioral base;
   everyone else stays on synthetic.
3. Monitor the live health-report/diversity/Open-Mindedness deltas + the shadow-divergence logs.
4. Ramp to 100% only if the Stage-4 gates hold in production.
5. **Rollback** at any point = swap the pointer back to the synthetic base
   (`corpus_refresh.py:16-18`); no redeploy, no data loss.

### 7.5 Decision gates

- **G1 (→ Stage 2):** enough production reads to clear k-core `5/5` on a non-trivial cohort.
- **G2 (→ Stage 3):** offline builder produces a valid `MINDData` + `FeedbackGraph`
  deterministically (pinned seed, MANIFEST).
- **G3 (→ Stage 4):** behavioral graph ≥ synthetic on the W8A battery — diversity no worse,
  homogenization flat-or-better, stability above floor, connectivity acceptable.
- **G4 (→ Stage 5):** shadow divergence is explainable and within tolerance; no regression in
  the health report or Open-Mindedness on the shadow cohort.
- **G5 (→ 100%):** canary shows neutral-or-better live metrics; rollback rehearsed.

Any gate failing ⇒ **stay at the prior stage**; the synthetic base keeps serving. No stage
after 4 changes serving without an explicit, reversible, flag-gated swap.
