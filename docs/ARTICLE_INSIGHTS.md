# Article Insights: AI summaries + bias analysis — design

**Status:** design approved for implementation (this doc is written first, per request); the
"Implemented" section at the end is filled in as the work lands.
**Date:** 2026-08-03.

## What it is

Two per-article artifacts, generated by an LLM, cached forever, and served read-only:

1. **Summary** — 2–4 sentences, factual, grounded *only* in the article's own title,
   description, and body excerpt. No outside knowledge, no speculation; if the text doesn't
   support a claim, the summary must not make it.
2. **Bias analysis** — how the article *frames* its subject: tone, loaded/emotive language
   (quoted), notable omissions ("what a reader isn't told"), and whose viewpoint the piece
   centres — explicitly **without** a left/right label. The scored registry lean already covers
   placement; this explains *how the writing works on the reader*, which a number cannot.

## Architecture (follows the repo's existing background-enrichment pattern)

The design template is the publisher-metadata enrichment (W4) and push delivery (B2): a store
table + accessors, a pure generator module, a bounded worker on the poller's post-cycle seam,
env-gated, dormant by default, provably zero-change when off.

```
ingest cycle ──▶ poller post-cycle seam
                   ├─ enqueue: INSERT pending article_insights rows for new catalog
                   │           articles (ON CONFLICT DO NOTHING — canonical URL is the
                   │           dedup key; a re-ingested URL never regenerates)
                   └─ process: claim up to RWE_INSIGHTS_BATCH pending rows whose
                               nextAttemptAt has passed → article_insights.generate()
                               → upsert ok/failed (+attempts, exponential backoff)

request path ──▶ store.get_insights(urls) — a cache-only batched read; NEVER generates.
                 API attaches a nullable `insights` object to article payloads.
web          ──▶ analyzer panel renders "AI summary" + "How this article frames it"
                 sections when insights are present; nothing otherwise.
```

### Components

| piece | file | contract |
|---|---|---|
| store table | `examples/store.py` | `article_insights`: `article_id` (canonical URL, PK), `status` (`pending/ok/failed`), `summary` TEXT, `bias` JSON, `model`, `attempts` INT, `next_attempt_at`, `generated_at`, `content_hash`. Accessors: `enqueue_insights(urls)` (idempotent), `claim_insights_batch(n, now)`, `finish_insights(id, ok, payload/err)`, `get_insights(urls)` (batched, ok-only) |
| generator | `examples/article_insights.py` (new) | `generate(article, client) -> dict` — builds the grounded prompt, calls the Messages API, validates/parses the structured JSON, enforces the 2–4 sentence bound and the no-label rule (rejects outputs containing left/right labels); pure & injectable (tests pass a fake client) |
| worker hook | poller post-cycle seam (`api_server` / feed poller) | `run_insights_cycle(store, limit)` — enqueue new + process batch; identical seam and failure isolation as push delivery: an exception never breaks ingestion |
| API | `api_fastapi.py` | article serializers attach `insights` (nullable) from one batched `get_insights` call per response — additive, no schema break |
| web | analyzer panel component + `web/messages/*` ×5 | render-when-present; loading nothing, requesting nothing extra (insights ride the existing article payload) |
| observability | `obs_metrics` | `insights_generate_ms` timer; counters `insights_generated_total`, `insights_failed_total`, `insights_served_total` |

### LLM call

- SDK: official `anthropic` Python package (added to requirements); model from
  `RWE_INSIGHTS_MODEL`, **default `claude-opus-4-8`**.
- One Messages API call per article, structured JSON output
  (`{"summary": str, "bias": {"framing": str, "tone": str, "loadedLanguage": [str],
  "omissions": str, "viewpoint": str}}`), `max_tokens` ≈ 700, temperature 0.2.
- The prompt passes ONLY the article's own text (title + description + body excerpt, capped
  ~6k chars) and forbids outside knowledge — grounding by construction; the validator rejects
  summaries longer than 4 sentences and any bias text that reduces to a left/right verdict.

### Cost control & failure handling

- **Dedup:** canonical URL is the primary key; `content_hash` (title+description) means a
  re-scored or re-fetched article regenerates only if its text actually changed.
- **Bounded spend:** `RWE_INSIGHTS_BATCH` per ingest cycle (default 6) + eligibility floor
  (description present, ≥ 200 chars) — the catalog's long tail of stubs is never sent.
- **Failures:** attempts + exponential backoff (`2^attempts × 10 min`), terminal `failed` after
  3; a missing API key, missing package, or `RWE_INSIGHTS_ENABLED` unset ⇒ the feature is
  **dormant**: no table writes, no behavior change, request path byte-identical (the repo's
  provably-off pattern).
- **No request-path generation, ever** — a cache miss serves `insights: null`, and the page
  renders exactly as today. Page performance is untouched by construction; the report verifies
  with before/after serve timings.

### Env

`RWE_INSIGHTS_ENABLED` (default 0) · `ANTHROPIC_API_KEY` · `RWE_INSIGHTS_MODEL`
(claude-opus-4-8) · `RWE_INSIGHTS_BATCH` (6) · `RWE_INSIGHTS_MIN_CHARS` (200) — all through the
compose allowlist.

## Trade-offs considered

- **On-demand generation at first view** (rejected): puts a multi-second LLM call on the
  request path or needs SSE plumbing; the poller seam already exists, and news articles'
  insights are immutable — pre-generation wins on both latency and simplicity.
- **Batch API** (deferred): halves cost at 24 h latency; the per-cycle cap already bounds
  spend, and freshness matters for a news product. Revisit if volume grows.
- **Summarize in the web tier** (rejected): the engine owns article identity, canonicalization,
  and the store; the web tier is stateless by design here.
- **Reusing the rule-based analyzer output as the "bias analysis"** (rejected): the existing
  analyzer serves registry-derived numbers; the requested artifact is *prose about framing*,
  which only generation produces. The two are complementary and both render.

## Test & measurement plan

- Unit: prompt grounding (body-only inputs), JSON parsing + rejection paths (5-sentence
  summary, left/right label leak), backoff arithmetic, enqueue idempotency, claim ordering.
- Store: accessor round-trips; dedup on conflicting enqueues; content-hash regeneration rule.
- API: serialization attaches insights when present, `null` when absent; one batched read.
- Worker: fake client (no network) — cycle respects batch cap, isolates exceptions, records
  metrics.
- E2E (Playwright): seeded ok-row renders summary + bias sections on the analyzer page; absent
  row renders neither.
- Measurements on the box: generation latency distribution (`insights_generate_ms`), cache-hit
  serve cost (`get_insights` added ms on the article endpoints, before/after), coverage %
  after N cycles.
